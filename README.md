# nixos-fleet

A Nix flake that configures the fleet's NixOS VMs on Proxmox. It holds one module per concern, the installer ISO, and seven commands that make the keys, build the ISO, and install, deploy to and reset a host. The ansible repo's `site.yml` calls those commands, and this page shows how to run each of them by hand.

Status: evaluated and built on a workstation, never run on a host. See [Not yet confirmed](#not-yet-confirmed).

## What it needs

- Nix with the `nix-command` and `flakes` features on. The flake was checked with Nix 2.34.7. Every other tool comes from the flake's pinned nixpkgs.
- An x86_64 Linux machine to build on.
- For anything that reads a secret: an age key that the fleet's sops files are encrypted for, in `SOPS_AGE_KEY` or `SOPS_AGE_KEY_FILE`.
- For anything that reaches a host: an SSH key the host accepts, in your agent or your SSH configuration.

## Placeholders

| Placeholder | Value |
| --- | --- |
| `<fleet-dir>` | Path of a checkout of the repository that describes the fleet, such as `/opt/fleet-private` |
| `<host>` | Name of the host in the inventory, which is the name of its file in `nixos/hosts/` |
| `<address>` | IPv4 address of the host |

## Quick start

The flake works with no access to a real fleet, because its default fleet is the one in `example/`.

```bash
git clone https://github.com/myah-mitchell/nixos-fleet.git
cd nixos-fleet
nix flake check
nix build .#nixosConfigurations.ex01.config.system.build.toplevel
```

The first command evaluates every example host and runs the formatting and shell checks. The second builds the system of the example host ex01.

## Layout

```text
flake.nix            inputs, one nixosConfiguration per host, the ISO, the commands, the checks
flake.lock           the pinned versions of nixpkgs, sops-nix and disko
lib/fleet.nix        reads the fleet's JSON files and stops on a missing key
modules/             one module per concern, all options under fleet.*
  options.nix        the options the JSON files fill in
  default.nix        the list of modules an installed host gets
  installer.nix      the system on the installer ISO
  auditd-rules/      the audit rules that name no store path
  ssh-banner/        the script that frames the SSH banner
packages/            Komodo Periphery, packaged from the upstream release
scripts/             the seven commands, as shell scripts
example/             a complete fleet with throwaway keys, the default fleet input
```

## The fleet input

The flake holds no host. What the fleet is comes in through the input named `fleet`, which is a plain folder and not a flake.

| File in the fleet | What the flake does with it |
| --- | --- |
| `nixos/fleet.json` | Values every host shares |
| `nixos/hosts/<host>.json` | One host. Each file becomes `nixosConfigurations.<host>` |
| `secrets/fleet.yaml` | sops file with the secrets every host reads |
| `secrets/hosts/<host>.yaml` | sops file with one host's own secrets. Optional |
| `secrets/host-keys/<host>.yaml` | sops file with the host's SSH host keys. Only the commands read it |
| `secrets/installer.yaml` | sops file with the installer ISO's SSH host key. Only the commands read it |
| `.sops.yaml` | Who can decrypt which file. Only `new-host-key` and `new-installer-key` write it |

The two JSON files are generated by the ansible repo's `nixos-sync.yml` from the inventory. The flake reads them as they are and never reads YAML. A key that is missing from a file stops the evaluation with a message that names the file and the key:

```text
error: nixos/hosts/ex01.json: network: missing key "gateway"
```

### Override the input

Name your own fleet with `--override-input`:

```bash
nix build .#nixosConfigurations.<host>.config.system.build.toplevel \
  --override-input fleet git+file://<fleet-dir> \
  --no-write-lock-file
```

`git+file` takes the files git tracks and nothing else, so an ignored or untracked file in the checkout never reaches the Nix store. A host file you have just generated is invisible until you run `git add` on it.

The commands take `--fleet <fleet-dir>` and do the override themselves. A folder that is not a git checkout is read with `path:`, which takes every file in it.

## What a host is made of

Every host gets the base modules. The `features` object in its JSON file switches the rest.

| Feature | What it adds |
| --- | --- |
| `firewall` | The NixOS firewall, a rate limit on new SSH connections, and the ports of the host's stacks |
| `docker` | Docker with `userns-remap`, the Docker disk, the persistent disk, and the folders and seed files of the stacks |
| `komodo` | Komodo Periphery as a system service. Needs `docker` |
| `nodeExporter` | Node Exporter on port 9100 with TLS and basic auth |
| `fail2ban` | fail2ban with the sshd jail. NixOS warns that it does nothing when `firewall` is off |
| `auditd` | The Linux audit system with the fleet's rules |
| `mail` | Postfix, sending mail for root to the admin list |
| `mosh` | mosh and its UDP ports |

The base modules cover packages, accounts, CA certificates, chrony, the network, sshd (keys only, no passwords) and its banner, journald and syslog forwarding, the swap file, the guest agent, GRUB, and the serial console.

Hosts never update themselves. `system.autoUpgrade` is off, and a host changes only when someone deploys to it.

### Disks

| Disk | Mount | Made by |
| --- | --- | --- |
| scsi0 | `/` | disko, at every install |
| scsi1 | `/var/lib/docker` | disko, at every install. Only with `docker` |
| scsi2 | `/srv/persist` | `install-host`, only when the disk holds no filesystem. Only with `docker` |

scsi2 is the persistent disk. It is not in the disko configuration, so an install cannot wipe it. It holds the container volumes and logs, the SSH host keys, the Periphery key, and the Node Exporter password, and all of them outlive a rebuild of the VM.

A host without `docker` has no persistent disk. Its `/srv/persist` is a folder on the OS disk, and `install-host` puts the host keys there again at every install.

### Stacks

The `stacks` object in a host's JSON file lists folders, seed files and firewall ports. The stacks module applies them as they are and names no stack itself.

- Folders are made by systemd-tmpfiles with the owner, group and mode from the file.
- Seed files are copied only when the target does not exist, so a file filled in on the host is never put back.
- A port with `allowFrom` set to `any` is opened to every address. A port set to `internal` is opened to `internalSubnet` only.

A port that Docker publishes bypasses the NixOS firewall, because Docker passes the connection to the container in the FORWARD chain and the firewall filters INPUT. On a Docker host, the stacks module therefore also drops new connections to an `internal` port in the `DOCKER-USER` chain, unless they come from `internalSubnet`. A port Docker publishes that the host's JSON file does not list is open to every address, as it was under ufw.

## Commands

| Command | What it does |
| --- | --- |
| `new-host-key` | Makes a host's SSH keys, stores them in sops, adds the host to `.sops.yaml`, and re-keys the secrets |
| `new-installer-key` | Makes the installer ISO's SSH host key and stores it in sops |
| `build-installer` | Builds the installer ISO with the fleet's installer key, and prints the ISO's path |
| `host-state` | Prints `installer`, `installed`, or `unreachable` for an address |
| `install-host` | Installs a host that is booted into the installer |
| `deploy-host` | Builds a host's configuration and activates it on the host |
| `reset-host` | Wipes the start of the OS disk and reboots, so the VM boots the installer again |

Every command prints its options with `--help`, exits with 0 on success, and on failure prints one line on stderr and exits with a non-zero code.

```text
nix run .#new-host-key -- --fleet <fleet-dir> <host>
nix run .#new-installer-key -- --fleet <fleet-dir>
nix run .#build-installer -- --fleet <fleet-dir> [--flake <flake>]
nix run .#host-state   -- [--user <user>] <address>
nix run .#install-host -- --fleet <fleet-dir> [--flake <flake>] [--build-on local|remote] <host> <address>
nix run .#deploy-host  -- --fleet <fleet-dir> [--flake <flake>] [--user <user>] [--build-on local|remote] [--action switch|boot|test|dry-activate] <host> <address>
nix run .#reset-host   -- [--user <user>] --yes-wipe <host> <address>
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--flake` | The flake the command came from | The flake to build the host from |
| `--build-on` | `remote` | `remote` evaluates here and builds on the target. `local` builds here and copies the result |
| `--user` | `ansible` | The account to log in to an installed host as |
| `--action` | `switch` | What `nixos-rebuild` does with the built system |

## Add a host

A new host takes an inventory entry and no new module.

1. Add the host to the inventory in `<fleet-dir>` and run the ansible repo's `nixos-sync.yml`. It writes `nixos/hosts/<host>.json`.
2. Make the host's keys:

    ```bash
    nix run .#new-host-key -- --fleet <fleet-dir> <host>
    ```

    The command writes `secrets/host-keys/<host>.yaml`, adds the host to `.sops.yaml`, and encrypts `secrets/fleet.yaml` again so that the new host can read it.
3. Commit the changed files in `<fleet-dir>`.
4. Check that the host evaluates:

    ```bash
    nix build .#nixosConfigurations.<host>.config.system.build.toplevel \
      --override-input fleet git+file://<fleet-dir> \
      --no-write-lock-file --dry-run
    ```

Running `new-host-key` again for the same host keeps its keys and changes nothing.

`new-host-key` expects each rule in `.sops.yaml` to list its recipients under `key_groups`, as the file in `example/` does. It rewrites the file with yq, which keeps comments and drops the blank lines between rules.

## Build the installer ISO

The ISO has an SSH host key of its own, the same at every boot, so that `install-host` can tell the fleet's installer from any other machine before it sends a host's private keys. Make the key once per fleet:

```bash
nix run .#new-installer-key -- --fleet <fleet-dir>
```

The command writes `secrets/installer.yaml` and adds a rule for it to `.sops.yaml`. Commit both. Then build:

```bash
nix run .#build-installer -- --fleet <fleet-dir>
```

The command prints the path of the ISO in the Nix store. It carries the keys in `adminSshKeys` and `deploySshKeys` from `nixos/fleet.json` as root's authorized keys, so build it again when those keys change.

The installer's private key is in the ISO and in the Nix store of the machine that built it, where every local account can read it. It is worth less than a host's key: it lets a machine pass for the installer, and nothing else.

The installer runs from memory and does four things:

- It takes its address, gateway and nameservers from the cloud-init drive that Proxmox attaches, and asks DHCP when there is no drive.
- It runs sshd for root, with keys only.
- It runs the QEMU guest agent.
- It has the file `/etc/fleet-installer`, which is how the commands tell it from an installed host.

`nix build .#installer-iso` without the command builds the ISO of the example fleet, with the example's installer key, which is public. Nobody can log in to it over SSH, since the private halves of the example's authorized keys were thrown away.

## Install a host

### Prerequisites

- The VM exists with its disks, and is booted into the installer.
- `nixos/hosts/<host>.json`, `secrets/host-keys/<host>.yaml` and `secrets/installer.yaml` are committed in `<fleet-dir>`.
- The installer was built by `build-installer` from the same `secrets/installer.yaml`.
- Your SSH key is one of the keys the ISO was built with.
- `SOPS_AGE_KEY` or `SOPS_AGE_KEY_FILE` holds the admin key or the deploy key.

### Steps

1. Check that the machine is the installer:

    ```bash
    nix run .#host-state -- <address>
    ```

    ```text
    installer
    ```

2. Install:

    ```bash
    nix run .#install-host -- --fleet <fleet-dir> <host> <address>
    ```

    On success the last line names the host:

    ```text
    install-host: <host> is installed and is rebooting
    ```

3. Wait for the reboot, then check again with `host-state`. It prints `installed`.

> [!WARNING]
> An install wipes the OS disk and the Docker disk of the machine at `<address>`. The persistent disk is formatted only when it holds no filesystem.

### What install-host does

In this order:

1. Decrypts the host's SSH keys and the installer's public key, so a missing sops key stops the install before anything is touched.
2. Checks that the target has `/etc/fleet-installer` and the installer's host key, and refuses to go on without both.
3. Runs the disko phase of nixos-anywhere, which partitions and formats scsi0 and scsi1.
4. Formats scsi2 as ext4 with the label `persist` when `blkid` finds nothing on it, and mounts it. A disk that holds anything other than ext4 stops the install.
5. Writes the host's SSH keys to `/srv/persist/host/ssh`.
6. Runs the install phase of nixos-anywhere and reboots.

Every connection `install-host` makes itself accepts the installer's host key and no other, and those connections carry the host's keys. nixos-anywhere makes its own connections and checks no host key: it passes `StrictHostKeyChecking=no` first, and ssh keeps the first value it gets for an option, so `--ssh-option` cannot change it. What nixos-anywhere sends is the system and the disk layout, which hold no secret in the clear. A machine that could take the installer's address between the two checks could still change what gets installed.

nixos-anywhere cannot override a flake input. `install-host` therefore writes a small flake in a temporary folder that re-exports this flake's hosts with the fleet input set to `<fleet-dir>`, and hands that one to nixos-anywhere.

## Deploy to a host

```bash
nix run .#deploy-host -- --fleet <fleet-dir> <host> <address>
```

The command runs `nixos-rebuild switch` against the host as the deploy account, which has passwordless sudo and is a Nix trusted user. With `--action dry-activate` it builds the system and prints what a switch would change, and changes nothing.

`deploy-host` checks the host against the ed25519 host key stored in `secrets/host-keys/<host>.yaml`. A deploy therefore needs `SOPS_AGE_KEY` or `SOPS_AGE_KEY_FILE` too, and it fails when the machine at `<address>` is not the host it should be.

## Reset a host

```bash
nix run .#reset-host -- --yes-wipe <host> <address>
```

The command overwrites the first 16 MiB of scsi0 and reboots the host. The BIOS finds nothing to boot on the disk and starts the installer ISO. The persistent disk is not touched, so the install that follows finds the host's data and keys where they were.

`reset-host` reads `/etc/fleet-host` on the target and compares it with the name after `--yes-wipe`. It does nothing when they differ. Before the wipe it stops Docker, so that the containers' data on the persistent disk is written out, and before the reboot the kernel writes out what is left and makes every filesystem read-only.

> [!WARNING]
> A reset destroys everything on the OS disk. The install after it also wipes the Docker disk.

## Secrets

Secrets are sops files in the fleet, encrypted for age keys. There are three kinds of key.

| Key | Who holds it |
| --- | --- |
| admin | A person |
| deploy | What runs the commands, in `SOPS_AGE_KEY` or `SOPS_AGE_KEY_FILE` |
| One per host | Nobody. It follows from the host's ed25519 SSH host key |

| File | Encrypted for | Keys inside |
| --- | --- | --- |
| `secrets/fleet.yaml` | admin, deploy, every host | `server-password-hash`, `komodo-onboarding-key` |
| `secrets/hosts/<host>.yaml` | admin, deploy, that host | None yet |
| `secrets/host-keys/<host>.yaml` | admin, deploy | The host's four SSH key files |
| `secrets/installer.yaml` | admin, deploy | The installer's ed25519 key pair |

A host's SSH keys are made before the host exists, so its secrets can be encrypted for it before it boots for the first time. `install-host` puts the keys on the host. On the host, sops-nix derives the age key from `/srv/persist/host/ssh/ssh_host_ed25519_key` and decrypts the secrets into `/run/secrets` at activation.

A host can never read `secrets/host-keys/`, its own file included.

### Change a secret

Edit the file with sops from inside `<fleet-dir>`, so that sops finds `.sops.yaml`:

```bash
cd <fleet-dir>
nix shell nixpkgs#sops -c sops secrets/fleet.yaml
```

`server-password-hash` is the password of root, the admin account and the client account, as a hash. Make one with:

```bash
nix shell nixpkgs#mkpasswd -c mkpasswd -m yescrypt
```

Commit the file and deploy to every host that reads it.

### The example fleet's keys

Every private key of the example fleet is committed under `example/keys/`, so that the checks can run anywhere. Those keys are public and protect nothing. See [example/README.md](example/README.md).

## Komodo Periphery

The flake runs Periphery from its own package and its own systemd service, not from the module in nixpkgs.

nixpkgs 26.05 has `services.komodo-periphery`, but its package is Komodo 1.19.5. The fleet's Komodo Core is version 2, and a version 2 Periphery connects out to Core with a key pair, which version 1 cannot do. `packages/komodo-periphery.nix` takes the `periphery-x86_64` binary of release v2.3.3 from the Komodo project's GitHub releases, pinned by hash.

To move to another release, change `version` and `hash` in that file. Once nixpkgs ships Komodo 2, the package can be dropped for the one in nixpkgs.

Periphery's key is at `/srv/persist/host/komodo/periphery.key`. Periphery makes it at first start, and it outlives a reinstall. The onboarding key comes from `komodo-onboarding-key` in `secrets/fleet.yaml` and reaches Periphery through its environment.

## Checks

`nix flake check` runs these:

| Check | What it proves |
| --- | --- |
| `hosts` | Every host evaluates down to the derivation of its system, and every secret a host asks for is in the sops file it names |
| `installer` | The installer evaluates |
| `formatting` | Every `.nix` file is formatted as `nixfmt` would |
| `shellcheck` | ShellCheck finds nothing in `scripts/` |
| One per command | The command builds, which includes ShellCheck on the packaged script |

There is no VM test. Format the Nix files with `nix fmt`.

## Verified

Checked on 2026-09-27 with Determinate Nix 3.21.1 on a workstation, against the example fleet. No host was involved.

- `nix flake check` passes.
- The systems of ex01 and ex02 build. ex01 is a Docker host with every feature on, ex02 is a host without Docker.
- The installer ISO builds, at 1.4 GiB.
- A fleet with a missing JSON key stops the evaluation with the file and the key in the message.
- A fleet given as a git checkout contributes its tracked files only, both through `--override-input` and through the flake that `install-host` writes.
- `new-host-key`, run against a copy of the example fleet, adds a host to `.sops.yaml` and re-keys `secrets/fleet.yaml`. The new host's key then decrypts that file and does not decrypt the host keys. A second run changes nothing, and a run without a usable sops key changes nothing.
- `host-state` prints `unreachable` for an address nothing answers on, after about five seconds.
- `install-host`, `deploy-host` and `reset-host` stop with one line when the target does not answer, and `install-host` stops before that when the sops key is missing.
- `build-installer` builds the ISO of the example fleet, and the ISO's closure holds the example's installer key. `new-installer-key` adds its rule once, and a second run changes nothing.
- The ssh options `install-host` uses accept an sshd that has the installer's key, and refuse one with any other key. Tested against a local sshd.
- A host's closure holds its own sops files and not the rest of the fleet's files.

## Not yet confirmed

Nothing in this repo has run on a machine, real or virtual.

- That the ISO boots on a Proxmox VM with SeaBIOS, takes its address from the cloud-init drive, and that its guest agent reports the address.
- `install-host` from start to end: the two phases of nixos-anywhere as separate runs, the persistent disk prepared between them, and a remote build on an installer that runs from memory.
- That an installed host boots from GRUB on scsi0, mounts `/srv/persist` in the initrd, and that sshd and sops-nix find the host key there.
- That a reinstall keeps a persistent disk that already holds a filesystem.
- `deploy-host` against a host, as the deploy account, with sshd's limit of two sessions per connection.
- `reset-host`: that overwriting the start of the disk and the reboot that follows leave the VM in the installer.
- That the audit rules load. One rule the kernel refuses makes the unit that loads them fail.
- Docker with `userns-remap` on NixOS, and the stacks' folders and seed files as systemd-tmpfiles makes them.
- The Periphery binary of release v2.3.3 on NixOS, and that it connects to Core and onboards.
- Node Exporter with the credentials made on first boot, and the vmagent container reading the two files in `/etc/node-exporter`.
- The firewall rules: the SSH rate limit, the rules that admit the internal subnet only, and the `DOCKER-USER` rules for ports Docker publishes.
- That the installer's sshd uses the key from the ISO and makes none of its own.
- fail2ban, syslog forwarding to the gateway, mail through Postfix, chrony, the swap file, and keystroke logging for sudo and su.
